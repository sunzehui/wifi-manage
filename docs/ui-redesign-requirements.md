# 随身 WiFi 用户管理后台改造需求

> 归档：2026-10-25 的一次性 UI/UX 改版需求稿，已完成，仅作历史参考，不代表当前实现。

## 一、项目背景

当前项目是一个随身 WiFi 设备管理后台，主要面向普通消费者，而不是开发者或专业运维人员。

现有页面采用深色主题、三列卡片布局，展示电池、网络信号、实时速率、流量统计、WiFi 信息、设备信息以及连接设备列表。

整体结构基本合理，但存在以下问题：

1. 部分卡片信息过于专业，普通用户难以理解。
2. 卡片之间的信息优先级不够明显。
3. 电池卡片内容较少，但占用了较大的展示空间。
4. 设备信息卡片展示了过多底层技术参数。
5. PC 端的布局不能直接适配移动端。
6. WiFi 配置和连接设备管理缺少足够明显的操作入口。

请基于现有项目代码，对页面进行一次完整的 UI/UX 优化。

**核心目标：保留现有功能和数据来源，优化信息架构、视觉层次、响应式布局和用户操作体验。**

不要仅仅修改颜色、字体或间距，也不要推翻现有项目技术架构。

---

## 二、设计原则

### 1. 面向普通用户

所有主要信息应使用通俗易懂的语言。

将专业网络术语转化为普通用户可以理解的表达：

| 当前名称 | 优化建议 |
|---|---|
| RSRP | 信号强度 |
| RSRQ | 信号质量 |
| SINR | 信号干扰情况 |
| RSSI | 信号强度 |
| PCI | 收起到高级信息 |
| 小区 ID | 收起到高级信息 |
| WAN IP | 网络地址 |
| ICCID | 收起到设备详情 |
| IMEI | 收起到设备详情 |

不要在首页直接展示所有技术参数。

专业参数可以保留在「设备详情」或「高级信息」中，避免删除现有数据能力。

### 2. 信息优先级

首页信息优先级按照以下顺序排列：

1. 设备是否联网、当前网络状态。
2. 电池电量与充电状态。
3. 当前上下行网速。
4. 本月流量使用情况。
5. WiFi 配置与连接设备管理。
6. 设备型号、固件版本及高级信息。

让用户打开页面后，第一眼就能了解设备是否正常工作。

### 3. 设计风格

保留现有深色科技风格，但降低视觉复杂度。

设计要求：

- 深色背景，避免纯黑。
- 卡片采用统一的圆角、边框和间距。
- 主要数值使用较高的视觉对比度。
- 辅助说明使用低对比度文字。
- 绿色表示正常或在线。
- 橙色表示需要注意。
- 红色表示异常或危险。
- 蓝色用于主要操作与辅助信息。
- 避免过度使用渐变、发光效果和装饰性图标。
- 保持页面简洁、现代、清晰。

## 三、PC 端布局要求

适配宽度 1024px 及以上的桌面设备。

### 1. 页面顶部

保留现有顶部区域：

- 产品 Logo
- 产品名称
- 设备型号
- 固件版本
- 网络连接状态
- 设备后台入口

优化布局：

左侧展示产品名称和设备型号。

右侧展示设备联网状态和设备管理入口。

减少顶部信息的拥挤感，保持单行布局。

### 2. 第一屏：设备运行概况

将当前第一行的三个卡片重新设计。

建议布局：

左侧：设备状态卡片。

展示：

- 电池电量
- 电池图标
- 充电状态
- 当前网络状态
- 运营商
- 网络类型，例如 4G LTE 或 5G

中间：网络速度卡片。

展示：

- 当前下载速度
- 当前上传速度
- 实时速率曲线
- 网络质量提示

右侧：流量使用卡片。

展示：

- 本月已使用流量
- 总流量额度（如果设备支持）
- 剩余流量（如果设备支持）
- 流量使用进度条
- 流量重置日期（如果设备支持）

注意：

不要凭空计算或生成设备不支持的数据。

如果没有流量套餐额度，则仅展示已使用流量，不要伪造剩余流量或百分比。

### 3. 第二屏：WiFi 管理与设备信息

采用两列布局。

左侧：WiFi 管理卡片。

展示：

- WiFi 开关状态
- WiFi 名称
- 加密方式
- 当前信道
- 已连接设备数量
- 修改 WiFi 名称
- 修改 WiFi 密码
- WiFi 开关操作

将修改 WiFi 配置设计为明显的操作入口。

修改密码时应提供密码显示/隐藏功能。

右侧：设备信息卡片。

首页仅展示：

- 设备型号
- 固件版本
- 设备运行时间
- 当前网络类型

增加「查看设备详情」入口。

SN、IMEI、ICCID、PCI、小区 ID、DNS 等专业信息放入详情页面或展开区域。

### 4. 第三屏：连接设备管理

连接设备列表保持 PC 端表格布局。

顶部展示：

- 当前在线设备数量
- 全部设备数量
- 搜索设备
- 在线 / 离线筛选

表格字段：

| 字段 | 说明 |
|---|---|
| 设备名称 | 优先展示用户自定义名称 |
| 设备类型 | 手机、电脑、平板等，无法判断时显示未知 |
| IP 地址 | 当前分配的局域网 IP |
| 在线状态 | 在线 / 离线 |
| 下载流量 | 设备累计下载流量 |
| 上传流量 | 设备累计上传流量 |
| 接入时间 | 最近一次接入时间 |
| 操作 | 设备详情、禁止接入等 |

操作按钮应符合实际后端能力。

如果后端没有禁止接入功能，不要添加无效按钮。

表格应具备：

- 合理的列宽
- 清晰的表头
- 适当的行高
- 在线状态颜色区分
- 适当的悬停效果
- 横向滚动或合理的响应式处理

不要因为追求视觉简洁而删除重要设备数据。

## 四、移动端布局要求

适配 320px 至 767px 的手机屏幕。

移动端不能直接将 PC 端的三列布局缩小。

采用单列布局，按照用户实际使用频率重新排列内容。

### 1. 移动端顶部

顶部采用紧凑布局：

- 左侧展示产品 Logo 和名称。
- 右侧展示联网状态。
- 设备型号、固件版本等辅助信息可以放在次级区域。

避免顶部占据过多垂直空间。

### 2. 移动端首页顺序

推荐顺序：

第一部分：设备状态。

展示：

- 当前网络状态
- 运营商
- 4G / 5G 网络类型
- 电池电量
- 充电状态

第二部分：实时网速。

展示：

- 下载速度
- 上传速度
- 实时速率曲线

图表应适配手机宽度，避免过小。

第三部分：流量使用。

展示：

- 本月已用流量
- 剩余流量（仅在有真实套餐额度时展示）
- 流量进度条
- 流量重置日期（如果有）

第四部分：WiFi 管理。

展示：

- WiFi 名称
- WiFi 状态
- 已连接设备数量
- 修改 WiFi 名称
- 修改 WiFi 密码

操作入口采用清晰的按钮或列表项。

第五部分：连接设备。

移动端不要直接展示 PC 端完整表格。

改为设备卡片列表。

每个设备卡片展示：

- 设备图标
- 设备名称
- 在线状态
- IP 地址
- 下载 / 上传流量
- 设备操作入口

设备名称和状态应位于卡片的主要视觉区域。

MAC 地址、接入时间等辅助信息可以通过展开详情展示。

第六部分：设备详情。

采用折叠面板或独立详情页面展示：

- 型号
- 固件版本
- SN
- IMEI
- ICCID
- DNS
- PCI
- 小区 ID
- 其他高级信息

默认折叠，避免影响首页浏览。

### 3. 移动端交互

要求：

- 页面不出现整体横向滚动。
- 所有主要操作按钮有足够的触控区域。
- 按钮触控区域建议不小于 44px。
- 输入框适配手机键盘。
- 弹窗在手机端优先使用底部弹层或全屏弹窗。
- 修改 WiFi 密码时，提供确认操作。
- 设备列表支持搜索和筛选。
- 设备列表在数据较多时保持流畅。
- 重要状态不能只依靠颜色表达。

## 五、响应式断点

建议采用以下断点：

- >= 1440px：宽屏 PC，页面最大宽度适当限制。
- 1024px - 1439px：普通 PC，使用三列或两列自适应布局。
- 768px - 1023px：平板，采用两列布局。
- 320px - 767px：移动端，采用单列布局。

具体断点应根据项目现有 CSS 框架进行调整。

优先使用 CSS Grid、Flexbox 和现有响应式工具。

避免使用大量固定宽度、固定高度以及针对单一设备的特殊样式。

## 六、功能与数据要求

本次改造属于 UI/UX 优化，不允许破坏现有业务逻辑。

必须遵守：

1. 保留现有 API 接口。
2. 保留现有数据字段。
3. 保留现有数据刷新机制。
4. 保留现有设备管理功能。
5. 不要将真实数据替换成静态数据。
6. 不要为了展示效果而伪造网络状态。
7. 不要新增没有后端支持的业务功能。
8. 不要擅自修改 API 请求结构。
9. 对于不存在的数据，合理展示「暂无数据」或隐藏对应区域。
10. 对于加载失败的模块，提供适当的错误状态。

如果需要新增交互，请优先复用现有功能和接口。

## 七、开发实施要求

请先分析当前项目的：

- 技术栈
- 页面组件结构
- API 数据结构
- 样式组织方式
- 现有响应式方案

然后再开始修改。

要求：

1. 优先复用现有组件。
2. 合理拆分页面模块。
3. 避免创建过多无意义的组件。
4. 保持变量、函数和组件命名清晰。
5. 避免重复 CSS。
6. 不要随意引入新的 UI 框架。
7. 不要破坏现有深色主题。
8. 确保 PC 和移动端使用同一套真实数据。
9. 确保页面在不同屏幕宽度下正常显示。
10. 修改后检查控制台错误和布局异常。

如果项目使用 Vue 3，优先遵循现有 Composition API 和组件风格。

如果项目使用 TypeScript，保持完整的类型定义，不要为了方便大量使用 any。

## 八、最终验收标准

完成后请检查以下情况：

### PC 端

- 页面整体结构清晰。
- 三列卡片布局在宽屏下合理。
- 电池、网络和流量信息突出。
- 实时速率图表尺寸合理。
- 连接设备表格完整。
- 不出现不必要的横向滚动。
- 卡片之间的间距统一。

### 移动端

- 页面采用单列布局。
- 首页信息优先级合理。
- 所有卡片适配手机宽度。
- 连接设备使用卡片列表。
- 所有操作可以通过触摸完成。
- 不出现页面整体横向滚动。
- 文本不溢出。
- 不出现卡片内容被裁切。
- 不出现过小的按钮。
- 图表能够正常显示。

### 交付要求

请直接修改现有项目代码，而不是只给出设计建议。

完成后说明：

1. 修改了哪些页面和组件。
2. 调整了哪些布局结构。
3. PC 端与移动端分别做了哪些适配。
4. 哪些功能保持原样。
5. 是否存在需要后端配合的功能。
6. 是否完成了响应式检查。
