## 原厂后台接口勘查（设备 192.168.1.1，平台 mifi）

免登录可直接取到原厂静态资源；菜单结构在 `xml/ui_mifi.xml`：

- 页签 `tRouter`（路由器）下：
  - `mReboot` → implFunction `objReboot`，xmlName **`reset`**
  - `mPowerOffRouter` → implFunction `objPowerOffRouter`，xmlName **`power_off`**（仅 `deviceinfo_devicetype == MIFI` 时显示）

「关闭路由器」实际请求：
`GET /xml_action.cgi?method=get&module=duster&file=power_off`（Digest 鉴权，**无 XML body**）
→ 前端显示「路由器正在关闭……」，50s 后 `clearAuthheader()` 回登录页。
前端实现：`js/panel/router/poweroff_router.js`，`_Reboot()` 里 `getData('power_off')` → `callProductXML`（`js/base/ajax_calls.js:346`）。
`js/panel/router/reboot_router.js` 同套路（`getData('reset')`）。

结论/对比：原厂「关闭路由器」不写任何配置字段，是把一个 action 文件名当触发器；写操作才走 `method=set&module=duster&file=<文件>` + XML body（如我们仪表盘的 `uapxb_wlan_basic_settings` 写 `wlan_enable=0/1`）。
未实测 power_off（一点整机断电，需物理开机）；GET 触发动作在同套 AJAX 里是孤例，也不排除该页面在本版固件是空壳。

多语言：`properties/Messages_cn.properties`（`mPowerOffRouter=关闭路由器`、`lQueryPowerOffRouter=确定要关闭路由器？`、`h1PowerOffRouter=关闭路由器`）。

## 「关闭 WiFi」开关的来历与风险（回答"是不是猜的"）

**有据可依，不是猜的**：原厂无线设置页 `js/panel/wireless/wireless_settings.js` 就在读写同一个字段
—— 62 行读 `wlan_enable`，156 行 `putMapElement(..., "RGW/wlan_settings/wlan_enable", ...)` 回填，
249 行 `postXML("uapxb_wlan_basic_settings", ...)` 提交；页面上是「启用/禁用」单选 `rdRadioWN`（`EDWirelessNW()` 关掉时隐藏整块 basic_settings）。
所以我们仪表盘的 toggle = 把官方单选做成按钮，文件名/字段/set 通道全对得上。

**但仓库里零实测证据**：`git log -S wlan_enable` 只有初始提交 2d5caf9、0e5c997；memory 里没有 toggle 实测记录。
注意我们写的是**局部 XML**（只含 `wlan_enable`），官方页面提交整块 `wlan_settings`（含 channel / band40_acs_enable / sec_channel）。
局部写是官方也用的手法（`qs_complete` 只写 management 下一个字段），大概率按键值合并，但未验证"会不会顺手改掉信道"。

## 关掉 WiFi 后如何回连（硬约束）

设备 `deviceinfo`：MF518A03_CN_MGX / model LV01 / PXA1802 / V5.8.2，`devicetype=MIFI`、**`ethportmode=0`（无网口）**。
- 无线侧没有回头路：AP 消失 → 192.168.1.1 不可达；仪表盘（8765）与 APK（8787）都走同一条无线链路，一起失联。
- **软件层无法自救**：任何"延时自动恢复"都要把 enable=1 发出去，而那时已经没有链路。这是硬结论。
- 只剩物理路径：USB（固件里 USB 主要用于 U 盘共享/升级，是否提供 RNDIS 让电脑访问 192.168.1.1 未验证）、机身实体按键。
- 重启多半无效：`wlan_enable` 是写进 basic_settings 的持久配置。
- 附带隐患：设备自带「WiFi 无客户端时自动关闭」（10–60 分钟，`lWifiAutoOffFun` / `lDisableWifiAutoOff`），开着的话同样会自己失联。

## 已实现：设备操作「重启 / 关闭设备」（用户选的方案 2）

关键认知：**这两个动作不是写字段，是把 action 文件名当触发器** —— `GET xml_action.cgi?method=get&file=reset|power_off`，
无 body、无 `<RGW>` 响应。所以单独建模，不塞进 `buildSetXml`。

- `public/core.js`：`DEVICE_ACTIONS` + `buildDeviceAction(kind)` → `{file:'reset'|'power_off', label}`
- 传输层：`server.js#triggerDeviceAction(file)` / `server.php#MifiSession::triggerAction(file)` / `gateway.js#triggerAction(file)`
  判定规则 = **只把认证被拒当失败**；设备执行中先断开连接属预期（否则用户会反复点）
- `POST /api/router {action:reboot|poweroff, confirm?}`（三处同形）；`poweroff` 缺 `confirm:true` 直接拒（Node 502 / PHP 400，路由层错误码存量不一致，未动）
- 前端：首页底部新增「设备操作」卡（重启=普通 / 关机=红描边）+ 两个弹层。关机弹层 = 红色标题 + 风险长文 +
  **勾选解锁**（复选框未勾选时确认按钮 disabled）
- 窗口期机制：`app.js` 新增 `setDeviceHold/deviceHeld`，`showErrorBanner` 在窗口期内不弹红条、pill 显示「重启中/已关机」；
  页内 `#holdBar` 显示进度（重启：已用时 N 秒；关机：设备已关机 + 「我已开机」按钮）。状态存 `localStorage.mifi_hold`，
  重进页面仍在（`renderHold` 里回填 `setDeviceHold`，否则红条会一起冒出来 —— 这个 bug 截图时抓到并修掉）
- 诚实性处理：设备对**不认识的文件也回 200 空响应**（实测 `__probe__` → `{dropped:false}`），不能凭返回成功断言重启。
  故加 `window.onDeviceDown` 钩子：只有「观察到设备真的掉线过」才说「已重启完成」，否则提示「可能不生效」

实测：`triggerDeviceAction('status1')`、`('__probe__')` 均返回 `dropped:false`（认证通道 OK，设备 200 无挑战头）。
**未实测 reset / power_off 本身**（会真重启/断电，需用户点头）。三态 UI 均已截图核对：关机弹层、重启弹层、重启中状态条、已关机状态条。
`node --test` 7 项通过（新增 `buildDeviceAction` 用例）；`php -l`、4 个 JS、index 内联脚本全绿。

## 合并「修改名称」+「修改密码」为一次操作
- 弹层 `ovSsid`/`ovPass` 合并为 `ovWifi`（名称 + 新密码 + 确认新密码，两个密码框带 👁 显隐），按钮区变 2 个并排：修改名称与密码 / 自动关闭设置
- 新 action `security`：一条 `method=set` 请求同时写 `uapxb_wlan_security_settings` 的 ssid+密码。
  关键风险点：设备返回的 `<ssid>` 是 UTF-16 hex 且 `<key>` 按模式分节点存放，**只发 ssid 有冲掉密码的风险**，
  所以改名称时服务端会先读设备原密码回填进同一条请求（`core.buildSetXml('security')` 要求有 password 才发完整档案）
- 改名不改密码时设备原密码从设备读（PHP/Node 都在 action 里做了）；前端校验：名称非空/≤32 字节（汉字3字节）、密码 8-63 位、两次一致
